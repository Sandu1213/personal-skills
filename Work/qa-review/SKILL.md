# QA Review

把用户要解决的问题、产物质量和人类审核成本放在同一个流程中。质量必须体现为可观察的结果与证据；视觉表现不能替代正确性。

## 1. Understand：先对齐目标

执行前用自己的话简短说明：“我理解你的目标是……；要解决的问题是……；完成后你应该能……。”区分明确要求与推断，不输出内部推理过程。

已明确的任务直接推进。只有会改变范围、验收或关键决策的缺失信息才提问；继续处理不依赖答案的部分。保留用户指定的格式、路径、参考和时间约束。

完成条件：能说明用户要获得的结果、主要使用者和使用场景，并识别关键未知项。

## 2. Define：把高标准转成验收条件

### 先深化，后定标准（不扩大范围）

非简单任务在写验收条件前先回答四问，答案写进工作记录：

1. 该领域顶尖从业者在这里会做、而用户没提的事。只保留能在同一目标下提高质量的项；会增加交付物或改变范围的，列为待用户决定项，不擅自执行。
2. 他们会从哪种最原始的材料出发（一手数据、源码、日志、原始文献、真实用户行为），而不是已被汇总或转述的材料。Build 阶段优先使用它。
3. 他们会用的具体方法与工具，优先用已有的技能与依赖。
4. 除 agent 和用户之外，什么能证明结果正确（测试或基准、原始来源对照、第三方工具、生产指标、真实用户操作）。把它写成必须条件，Verify 阶段按它判定；拿不到时标为未验证，不用自评代替。

选择当前任务的领域标准，写下少量关键验收条件及各自的验证方法。分开记录必须通过的条件与值得提升的品质；不要靠平均分掩盖关键失败。

- **网站 / 产品 UI**：以有机会达到 Awwwards、Webby Awards、FWA 等优秀设计品质为审美志向，具体检查信息层级、字体与空间节奏、品牌一致性、交互反馈、响应式、可访问性和性能。业务工具优先完成用户任务。用户品牌、设计系统与用途决定风格，动画和视觉复杂度服务内容。这个志向不是官方评分或获奖保证。
- **代码 / API**：以行为正确、接口清楚、边界可靠、可维护和必要的回归验证为标准。先遵循仓库规则与现有实现。
- **研究 / 技术方案**：以证据可追溯、假设明确、选项可比较、结论能支持决策为标准。核查时效敏感事实，区分事实、推断与建议。
- **文档 / 演示 / 数据**：以受众可理解、论证完整、数字可靠、结构清楚、呈现可使用为标准；数据应有口径、单位和来源。

需要领域细节时使用现有专门技能；本技能负责质量协调，不重写它们的工作流。要求 local-review 的环境以其为最终交付门禁，评审期间不再启动简化或递归评审。

选取实际相关的参考。需要外部参考时查阅可访问的原始材料，注明来源；无法访问时说明限制。不要声称看过未读取的案例，也不要为了套用网站奖项而给非网站任务增加视觉装饰。

完成条件：每条必须条件都能通过检查、场景操作、证据核对或明确的专业判断来评估。

## 3. Build → Inspect → Improve：按缺陷迭代

先产出完整、可检查的版本。逐项对照验收条件，找出最影响用户目标的差距，修复后复查受影响的部分。

自检顺序：目标与内容正确性 → 主要流程和边界 → 可理解与可使用 → 视觉与表达品质。修复实际差距，不为展示努力反复重写已达标内容。

在工作记录中保留“问题 → 修改 → 复查证据”。简单任务可在对话中记录；复杂任务放进已授权的项目工作文件，不强制创建报告。

持续改进直到必须条件通过、主要品质差距关闭。两次连续迭代没有可验证进展，或遇到缺失权限、资料、工具及明确预算边界时，记录卡点和下一项必要行动，停止无效打磨。此时不声称达标；仍可继续独立且有价值的工作。主观品质问题用具体观察说明，不用虚构评分代替证据。

## 4. Render：选择降低理解与审核成本的介质

先判断人需要看什么、比较什么或操作什么，再选择足够表达它的最轻形式。沿用前文 Karpathy 讨论中的 Render Layer 思路，不把介质当成从低到高的排名。

| 审核需求 | 首选形式 | 采用条件 |
| --- | --- | --- |
| 结论、步骤、证据、小规模比较 | Markdown / 表格 | 文字已经能清楚支持判断 |
| 架构、依赖、流程、空间关系 | Mermaid / SVG | 图能减少读者追踪关系的负担 |
| 多维比较、参数变化、筛选与探索 | Interactive HTML | 操作能帮助回答实际问题 |
| 时序变化、运动机制、难懂的动态概念 | Animation / Video | 动态表达比静态图有明确理解收益 |

用户明确要求某种格式时优先满足。底层结果和依据先成立，再制作呈现；为了解释复杂关系，可更早做最小草图。关键结论、数据和限定条件保持一致，图表或动画不能偷偷增加未经验证的事实。

交互产物提供关键结论与静态摘要；动态产物提供文字说明、暂停或可访问的替代方式。使用示例数据时明显标注。优先已有工具与依赖；需要付费服务、凭据或额外外部操作时遵循当前授权边界。工具不可用时交付可用替代并准确说明，不能把分镜稿称为已生成视频。

完成条件：读者能定位结论、查看依据，并用该形式完成预期审核，而不是只看到漂亮展示。

## 5. Verify：验证结果和呈现

以实际执行结果为证据，并标记每条必须条件为通过、失败或未验证。

- UI：查看实际渲染，在相关桌面与移动尺寸操作主要流程；检查关键状态、键盘操作和内容溢出。
- 代码：运行与变更风险相称的项目检查，覆盖关键失败路径；启动失败或无法运行的检查记录为未验证。
- 研究 / 数据：核对决定结论的来源、计算和单位；让摘要与底层依据一致。
- 文档 / 图 / 交互 / 视频：打开或渲染最终产物，检查链接、标签、交互、画面或时间线；按需使用对应领域技能。

交付门禁：全部必须条件通过且主要品质差距关闭，才称为完成。存在关键失败则报告受阻；证据不足则报告未验证或部分完成。明确区分“已制作”与“已验证”。自检不能替代环境要求的独立评审。

最终简短给出结果与入口、主要验证证据、尚存限制及必要的下一步。让用户无需阅读过程消息也能判断是否可用。

## 6. Self-improve：从反馈改进，不自动改写规则

在本任务内应用用户反馈，并复查改动是否解决了原问题。发现可复用经验时，说明触发场景、可观察失败、修正方法和适用边界。

仅在用户明确授权更新技能、规则或长期记忆时持久化这些经验；否则作为建议交付。经过实际使用再提炼规则，避免把一次偏好变成所有任务的固定流程。

需要验证本技能的路由和门禁时，读取 [references/acceptance-cases.md](references/acceptance-cases.md)。这些案例是行为评估输入，不代表已经完成真实任务测试。
